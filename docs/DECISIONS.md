## DEC-001 사용자 지정 버전만 기록

- 결정 당시 버전: 1.3.0 문서 체계 구축 작업
- 상태: 유효
- 결정: 프로그램 버전은 사용자가 현재 채팅에서 직접 명시한 값만 사용한다.
- 배경·이유: 폴더명, 빌드 파일과 Git 기준이 서로 다를 수 있어 자동 추정은 다른 버전 기록을 오염시킨다.
- 검토한 대안: `APP_VERSION`, 최신 태그 또는 폴더명에서 자동 추정.
- 사용하지 않는 방식: Codex가 자동으로 patch/minor 버전을 올리는 방식.
- 영향: `AGENTS.md`, `docs/VERSION_INDEX.md`, `docs/versions/`.
- 장점/단점: 기록 오염을 막지만 사용자가 버전을 말하지 않으면 버전 문서를 시작할 수 없다.
- 변경 조건: 사용자가 명시적으로 자동 버전 정책을 승인할 때.
- 관련 요구사항: DOC-001.

- 변경 조건: 다른 백엔드가 동일한 포맷·취소·패키징 요구를 검증했을 때.

- 결정 당시 버전: 1.3.0
- 상태: 유효

- 배경·이유: 모든 설정을 처음부터 펼치면 정보 위계와 탐색성이 무너지고 사용하지 않는 효과도 처리 대상으로 오해하기 쉽다.

- 영향: `stage4_design_effects.py`, `app.py`, `ui_state.py`.
- 장점/단점: 화면이 짧고 의도가 명확하다. 현재 카드 순서는 inspector 정리 순서이고 기존 renderer 합성 의미 순서는 바꾸지 않는다.
- 변경 조건: renderer가 명시적 scene graph와 다중 인스턴스 z-order를 지원할 때.
- 관련 요구사항: EFFECT-002, UI-005, SAVE-001.

## DEC-012 환경음은 독립 버스로 최종 반복 타임라인에 합성

- 결정 당시 버전: 1.3.0
- 상태: 유효
- 결정: 음악과 환경음을 별도 bus로 혼합하고 meter stem을 생성한다. 완성 영상을 여러 번 반복할 때 환경음은 1회 결과 안에 굽지 않고 최종 반복 media 위에 연속 타임라인으로 다시 합성한다.
- 배경·이유: 1회 환경음 패턴까지 그대로 반복하면 경계가 들리고, music/ambient/master 레벨을 독립적으로 확인할 수 없다.
- 대안: 모든 오디오를 단일 `amix`에 넣거나 반복된 영상 조각마다 환경음을 다시 시작.
- 사용하지 않는 방식: 전체 환경음을 Python 메모리에 적재, 렌더 마지막에 단순 master gain만 적용.
- 영향: `audio_pipeline.py`, `stage4_design_effects.py`, `stage5_render.py`.
- 장점/단점: 장시간 출력에서도 메모리를 일정하게 유지하고 반복 경계를 완화한다. 대신 반복 출력은 환경음 후처리 FFmpeg 단계를 한 번 더 수행한다.
- 변경 조건: 이벤트 기반 환경음 scheduler 또는 별도 audio render graph 도입 시.
- 관련 요구사항: AUDIO-004, REPEAT-001, RENDER-001.

## DEC-013 시작 화면은 작은 네이티브 런처가 소유

- 결정 당시 버전: 1.3.0
- 상태: 1.3.1에서 대체됨
- 결정: Windows 배포 진입점은 약 29KB WinForms 런처로 만들고, per-pixel alpha 레이어드 창에 배경 없는 심볼을 즉시 표시한다. core의 Tk 로딩 스플래시가 보이면 네이티브 창을 닫고, 로딩 스플래시는 실제 메인 창이 준비될 때 닫는다.
- 배경·이유: PyInstaller 내장 스플래시는 Tcl 초기화 뒤에야 보여 cold start에서 약 18초 동안 아무 피드백이 없었다.
- 대안: Tk 스플래시만 사용하거나 PyInstaller `--splash`만 사용.
- 사용하지 않는 방식: 컬러키 투명 처리, 그라데이션 halo, PyInstaller 내장 스플래시, 별도 UI 프레임워크.
- 영향: `native_launcher.cs`, `app.py`, `app_splash.png`, Windows build scripts와 배포 파일 구조.
- 장점/단점: 첫 피드백은 수 초 이내이고 장시간 로딩에는 실제 작업 문구·진행 바가 보인다. 배포 폴더에는 launcher, core, splash 세 항목이 필요하다.
- 변경 조건: bootloader 단계에서 동등하게 즉시 표시되는 공식 패키징 경로를 채택할 때.
- 관련 요구사항: UI-002, UI-006, PERF-001, BUILD-001.

## DEC-014 릴리스는 양 플랫폼 빌드 성공 뒤 게시

- 결정 당시 버전: 1.3.0 종료
- 상태: 유효
- 결정: GitHub Actions는 Windows와 macOS 패키지를 각각 artifact로 만든 뒤 두 job이 모두 성공한 경우에만 publish job이 태그 릴리스와 네 자산을 게시한다.
- 배경·이유: 한 플랫폼만 성공한 상태에서 반쪽짜리 정식 릴리스가 먼저 공개되는 것을 막는다.
- 대안: 각 플랫폼 job이 릴리스에 직접 업로드하거나 로컬에서 수동 업로드.
- 사용하지 않는 방식: Windows 성공 직후 릴리스를 먼저 만들고 macOS 실패를 나중에 발견하는 흐름.
- 영향: `.github/workflows/build.yml`, `release_notes.md`, `setup.bat`, `setup_mac.sh`.
- 장점/단점: 공개 릴리스의 원자성이 높다. 두 플랫폼 중 하나가 실패하면 자산이 전혀 게시되지 않는다.
- 변경 조건: 플랫폼별 독립 prerelease 정책을 사용자가 명시적으로 요구할 때.
- 관련 요구사항: BUILD-001.
